# Audit: run_picks.py — Lines 1–3000
## Summary

Lines 1–3000 cover all imports, constants, math engine, gates, rules, sizing functions, the CSV parser, the full OddsFetcher class, odds-parsing helpers (extract_player_props, extract_game_lines, extract_team_totals, extract_alt_spreads), the player-matching layer, and the main prop and game-line evaluation pipelines (evaluate_props, evaluate_game_lines) plus the start of the F5-line evaluator. The architecture is generally sound and the shadow-split logic, file-lock discipline, and distribution routing are mostly correct. However, several real bugs exist: a latent NameError on `log.warning` inside `evaluate_game_lines`, two `datetime.now()` calls missing timezone info, a stale old-edge-ceiling (20%) in `log_candidates`, a missing `pick_score` on R4/R11 shadow picks before they hit `size_picks_base`, a silent `except Exception: pass` swallowing all cache-save errors, a WNBA early-season `datetime.now()` missing timezone, and a PTS comment inconsistency in the KILLSHOT allowlist. Several medium/low findings around team-name substring collisions, game-total projection matching, and the dead T4 VAKE entries are also documented below.

---

## Findings

- **[CRITICAL]** `run_picks.py:2478` — **WHAT**: `log.warning(...)` uses the name `log`, which is never defined anywhere in this file. The module logger is named `logger` (line 116). **WHY WRONG**: This is a latent `NameError` that fires only when `GAME_SIGMA` does not contain the sport key (e.g. a new sport is added without a sigma entry). It would crash the run at that exact point instead of gracefully skipping game lines. **FIX**: Change `log.warning` to `logger.warning`.

- **[HIGH]** `run_picks.py:1029` — **WHAT**: `datetime.now().date()` inside `check_prop_gates` (WNBA opening-gate block) has no timezone. **WHY WRONG**: CLAUDE.md mandates `ZoneInfo("America/New_York")` for all `datetime.now()` calls. Without a timezone this reads system local time; on a Windows machine set to Mountain or Pacific time the gate can fire one day early or late around midnight. **FIX**: Replace with `datetime.now(ZoneInfo("America/New_York")).date()`.

- **[HIGH]** `run_picks.py:2457` — **WHAT**: `datetime.now().date()` inside `evaluate_props` (WNBA early-season score dampener) has no timezone. **WHY WRONG**: Same reason as line 1029. The score dampener applies the wrong multiplier if the system clock and ET diverge at day boundaries. **FIX**: `datetime.now(ZoneInfo("America/New_York")).date()`.

- **[HIGH]** `run_picks.py:3975` — **WHAT**: `__import__("datetime").datetime.now()` in `log_candidates` is naive (no timezone). **WHY WRONG**: Every other `run_time` in the file uses `datetime.now(ZoneInfo("America/New_York"))`. This call produces a naive datetime from system local time. The run_time column in `pick_log_candidates.csv` will be wrong for non-ET system clocks and is inconsistent with every other log writer. **FIX**: Replace with `datetime.now(ZoneInfo("America/New_York"))` using the already-imported `ZoneInfo`.

- **[HIGH]** `run_picks.py:1195–1211` — **WHAT**: `apply_hard_rules` appends R4/R11 kills to `shadow_dest` without setting `pick_score`. **WHY WRONG**: When these picks later reach `size_picks_base` (line 6227) and then `log_picks`, the `pick_score` key is absent/`None`. `log_picks` writes `f"{p.get('pick_score', 0):.1f}"` which defaults to `"0.0"` — the shadow log silently records every R4/R11 kill as a 0.0-score pick, making them useless for analysis. The `pick_score` was never set because `apply_hard_rules` fires before `check_prop_gates` assigns it. **FIX**: Before appending to `shadow_dest`, compute and store `pick_score` using `pick_score()` with the pick's `win_prob`, `adj_edge`, mode, and tier — or at minimum leave a sentinel like `None` and filter in `log_picks`.

- **[HIGH]** `run_picks.py:1806–1807` — **WHAT**: `_save_cache` swallows all exceptions with a bare `except Exception: pass`. **WHY WRONG**: A cache write failure (disk full, permissions, path error) is silently ignored. Every subsequent run re-fetches all odds from the Odds API, burning rate-limit quota with no diagnostic. The comment-note at C9 on line 1794 explicitly called out `pass` as wrong in the context of the load function. **FIX**: At minimum `logger.warning("Cache save failed: %s", e)` so the issue surfaces in the log. Do not raise (non-critical path), but do not silently swallow.

- **[MEDIUM]** `run_picks.py:3983` — **WHAT**: `_old_score` inside `log_candidates` uses edge ceiling `/ 20` (20%), while the live `pick_score` function at line 919 uses `/ 15` (15%). **WHY WRONG**: The reference formula label is `score_old_6040` and its intended purpose is to preserve the pre-refactor score for comparison, but the 20% ceiling was the old ceiling from an even earlier version — the refactor that changed the formula to 40/60 also changed the ceiling to 15%. The column therefore compares against the wrong historical baseline. **FIX**: Verify whether 20% was truly the ceiling under the 60/40 formula. If so, document clearly; if not, correct to match the actual old formula parameters.

- **[MEDIUM]** `run_picks.py:198–199` — **WHAT**: `KILLSHOT_STAT_ALLOW` includes `PTS` but the inline comment says "PTS: manual override only — PTS is T2, so tier check fires before stat check for auto-qualify." This means PTS will never auto-qualify (tier gate at line 5300 blocks T2). **WHY WRONG**: PTS being in the frozenset is misleading dead code for the auto-qualify path. If it's truly manual-only, removing it from the frozenset would make the intent unambiguous; leaving it creates confusion about whether PTS auto-qualifies and whether the stat gate is a redundant check. **FIX**: Either remove PTS from `KILLSHOT_STAT_ALLOW` and rely on manual override to bypass the gate entirely, or add a separate `KILLSHOT_MANUAL_STAT_ALLOW` set and document clearly.

- **[MEDIUM]** `run_picks.py:506–510` — **WHAT**: `VAKE_MULT` contains a `"T4"` key (`variance: 0.40`, `tier: 0.35`) but T4 was removed when golf code was archived. **WHY WRONG**: The T4 entries are dead code. `VAKE_MULT["variance"].get(tier, 0.85)` in `size_bonus_pick` (line 1495) would use the fallback `0.85` for any tier not in the dict anyway, so T4 is unreachable. Minor clutter but could mislead a future reader into thinking T4 is still active. **FIX**: Remove T4 entries from `VAKE_MULT`.

- **[MEDIUM]** `run_picks.py:613–621` — **WHAT**: `resolve_team_abbrev` step 2 (substring check) compares `full_name in low or low in full_name` without a length guard. **WHY WRONG**: Short 3-letter names like `"uta"` (Utah Jazz, Utah Hockey Club) are substrings of many team names (`"atlanta"` contains `"a"`... actually `uta` is in `"tampa bay…"`). More concretely `"uta"` is in `"utah hockey club"` AND `"utah jazz"` — but `TEAM_ABBREV` maps both to `"UTA"`, so that specific case is fine. However `"dal"` is in `"dallas mavericks"` AND `"dallas stars"` — both map to `"DAL"`, so also fine. The real risk is that a multi-sport TEAM_ABBREV collision (e.g. `"BOS"` maps to both "boston celtics" and "boston bruins") means step 2 could return the wrong sport's abbreviation when the API sends a team name from one sport and the code is running another. **FIX**: At minimum document the cross-sport collision risk. For production safety, pass `sport` into `resolve_team_abbrev` so it only checks same-sport entries.

- **[MEDIUM]** `run_picks.py:2505–2515` — **WHAT**: The TOTALS projection-matching loop (`find_team_proj` shortcut path) iterates all `team_proj` keys and checks `if tk in home_name or home_name in tk` using uppercase string containment. **WHY WRONG**: This is essentially the same bug as the old substring-matching NRFI approach that was fixed by `resolve_team_abbrev`. E.g., if `tk="SEA"` and `home_name="SEATTLE MARINERS"`, `"SEA" in "SEATTLE MARINERS"` is `True` — this works by accident. But `tk="LAD"` and `home_name="LOS ANGELES DODGERS"`: `"LAD" not in "LOS ANGELES DODGERS"` — this fails. The function already has `find_team_proj` which correctly uses `resolve_team_abbrev`, but the TOTALS block in `evaluate_game_lines` (lines 2506–2514) rolls its own inline match instead of calling `find_team_proj`. **FIX**: Replace the inline loop with `find_team_proj(home_name, team_proj) or find_team_proj(away_name, team_proj)`.

- **[MEDIUM]** `run_picks.py:2214` — **WHAT**: In `extract_team_totals`, the `team` field is parsed from `outcome.get("description", outcome.get("name", ""))`. When `description` is absent, `name` is `"Over"` or `"Under"` — not the team name. **WHY WRONG**: If the Odds API response for team totals omits the `description` field (which varies by book), the fallback `name` will be `"Over"` or `"Under"`, polluting `by_line` with `("Over", point)` and `("Under", point)` as team keys. The downstream `find_team_proj("Over", ...)` will silently return `None` and the pick is skipped — so no wrong pick is generated, but valid team totals are silently dropped. **FIX**: Add a guard: `if team in ("Over", "Under"): continue` after parsing the team from outcomes.

- **[MEDIUM]** `run_picks.py:1029` — **WHAT**: `today_date = datetime.now().date()` in `check_prop_gates` — this is called in a per-pick loop inside `evaluate_props`. The `datetime.now()` is called fresh for every pick. **WHY WRONG**: Calling `datetime.now()` in a tight per-pick loop is a minor inefficiency (thousands of syscalls). More important is the timezone issue already noted above. **FIX**: Compute `today_date` once before the loop in `evaluate_props` and pass it in, or use a module-level cached value. This is LOW severity independently but the missing-tz issue elevates it.

- **[MEDIUM]** `run_picks.py:6197–6199` — **WHAT**: When `qualified` is empty after splitting shadow sports but `shadow_picks` is non-empty, the function returns early with `"No qualifying picks found"` but the shadow picks have already been logged (line 6204–6209). **WHY WRONG**: This is not a bug per se, but the early-return message is misleading: it says "no qualifying picks" when shadow WNBA picks DID qualify and were logged. A developer reading the output would be confused. **FIX**: Print a clearer message distinguishing shadow-only runs, e.g. "No live-sport qualifying picks (shadow picks logged separately)."

- **[LOW]** `run_picks.py:508–509` — **WHAT**: `PICK_SCORE_TIER_MULT` (line 520–526) does not have a `"T1B"` entry with the same 0.93 value that `VAKE_MULT` has for T1B. Actually line 521 shows `"T1B": 0.93` is present. No issue here — confirming correct.

- **[LOW]** `run_picks.py:327–348` — **WHAT**: `SIGMA` dict includes `"REC": {"mult": 0.50, "min": 1.2}` but `REC` (receptions) is also in `POISSON_STATS` (line 356). **WHY WRONG**: `calc_prop_prob` checks `POISSON_STATS` first (line 767), so the `SIGMA["REC"]` entry is unreachable dead code for single-stat `REC` props. The only reachable path for `SIGMA["REC"]` would be the `_combo_mu_sigma` path if REC were in a combo stat, but it's not in `COMBO_STATS`. **FIX**: Remove `"REC"` from `SIGMA` to avoid confusion. Add a comment in `POISSON_STATS` noting that `SIGMA["REC"]` exists but is dead.

- **[LOW]** `run_picks.py:500–501` — **WHAT**: `TIERS["T2"]` includes `"SV"` but `SV` is also in `SIGMA` with a calibrated value and in `SHADOW_STATS`. The `TIERS` definition is fine, but `KILLSHOT_STAT_ALLOW` could theoretically accept a `SV` pick through the auto-gate if `SV` were T1. Since `SV` is T2, the tier gate blocks it. No real bug, just worth noting `SV` is in T2 for the record. Confirmed no issue.

- **[LOW]** `run_picks.py:1083–1086` — **WHAT**: G14 comment says "NB stats (3PM) are exempt for NBA/NHL" but the code exempts ALL NB_STATS (not just 3PM) when `stat not in NB_STATS` is the condition. This means `HRR`, `HA`, `REB`, `AST`, `RBI`, `ER`, `TB` also skip G14. **WHY WRONG**: The comment is misleading — it understates the scope of the exemption. For newly-added stats like `RBI` (r=0.87, heavy zero-inflation), G14's "directional conviction" check might actually be useful. **FIX**: Update the comment to say "all NB_STATS are exempt" and document the rationale (NB handles sub-line projections correctly via distribution).

- **[LOW]** `run_picks.py:1727–1728` — **WHAT**: The CSV parser swallows `ValueError, KeyError` silently with `except (ValueError, KeyError): continue`. **WHY WRONG**: A malformed row (e.g. a tab in a field causing a key offset) is skipped without any log warning. On a bad SaberSim export this could silently drop an entire roster. **FIX**: Add `logger.debug(f"Skipped malformed row: {e}")` so issues surface in the log without crashing.

- **[LOW]** `run_picks.py:334` — **WHAT**: `SIGMA["REB"]` comment says "was 0.58/2.5" — this is a historical record, not an issue. Confirmed correct per CLAUDE.md.

- **[LOW]** `run_picks.py:568–569` — **WHAT**: `TEAM_ABBREV` maps both `"la clippers"` and `"los angeles clippers"` to `"LAC"`, and both `"la lakers"` and `"los angeles lakers"` to `"LAL"`. These are intentional duplicates and correct. However `ABBREV_TO_NAMES` (built at line 600–601) will accumulate both entries for `"LAC"` and `"LAL"`. No bug, but `ABBREV_TO_NAMES` is built but never used within lines 1–3000 (and may not be used anywhere); if unused it is dead code. **FIX**: Verify `ABBREV_TO_NAMES` usage; remove if unused.

- **[LOW]** `run_picks.py:1861` — **WHAT**: The event-filter log line says `"MST"` hardcoded: `"Local date: {local_date} MST | Now UTC..."`. **WHY WRONG**: The variable `CO_TZ = ZoneInfo("America/Denver")` handles DST automatically (MDT in summer), but the printed label always says "MST". **FIX**: Use `local_now.strftime("%Z")` to get the dynamic timezone abbreviation (`MST` vs `MDT`).

- **[LOW]** `run_picks.py:356` — **WHAT**: `POISSON_STATS` comment at end says "AST/REB moved to NB_STATS" — this is correct per CLAUDE.md. Confirmed.

- **[OPEN_QUESTION]** `run_picks.py:1083–1084` — **WHAT**: G14 states "NB stats (3PM) are exempt — NB distribution handles these correctly" but the comment on line 1080 says "Normal/SIGMA stats (PTS, OUTS, HA, TB): proj must clear line by ≥0.10σ." `TB` is in `NB_STATS` (r=1.3) — so G14 DOES apply to TB only when `sigma_override > 0` (H3 path); otherwise `TB` is in `NB_STATS` and skips G14. Is this intentional? TB at low lines (1.5) with a near-line projection could theoretically pass with a tiny NB edge. The TB path is in SHADOW_STATS anyway, so the practical impact is zero for now, but needs clarification when TB goes live.

- **[OPEN_QUESTION]** `run_picks.py:613–621` — **WHAT**: `resolve_team_abbrev` step 2 checks `full_name in low or low in full_name`. For a 2-character API name like `"sf"` (San Francisco), `"sf" in "san francisco giants"` is `False`, but `"san francisco giants" in "sf"` is also `False`. However for `"la"` (used in `"la clippers"`, `"la lakers"`, `"la dodgers"`, `"la angels"`), `"la" in "la clippers"` is `True` and returns the first match found. Since dict iteration order is insertion order, this is deterministic but could return the wrong LA team if the API sends a bare `"la"` team name. This is unlikely in practice but a known fragility.
