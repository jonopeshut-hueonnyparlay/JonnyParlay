# run_picks.py Audit — Lines 3001–5872 (Part 2)

## Summary

Lines 3001–5872 cover: the NRFI/YRFI evaluator, deduplication (3-pass), game-line correlation filter (GLC), alt-spread parlay builder, `log_candidates`, `log_picks`, all Discord posting functions (`post_to_discord`, `post_daily_lay`, `post_longshot`, `post_extras_to_discord`, `post_killshots_to_discord`), KILLSHOT selection/sizing logic, and the main() function from CSV parsing through all posting flows to SGP integration. The overall architecture is sound: shadow split happens after `size_picks_base` and before `apply_caps`, the FileLock pattern is consistently applied on every pick_log write path, and the discord guard test-and-set (`_discord_claim_post`) is used correctly before every webhook post. Several real issues are found: a silent timezone-naive `datetime.now()` in `log_candidates`, the `MAX_PREMIUM_PICKS=3` constant conflicts with multiple hardcoded `[:5]` slices in the embed builder and output formatter, the 12u cap enforcement omits same-session daily_lay/longshot units when checking KILLSHOT fit, a dead MLB entry in `SHADOW_LOG_PATHS`, a schema-invalid `run_type="gameline"` written for manual game-line picks, the all-picks sanity check falsely flags KILLSHOTs as oversized (in-place mutation of `qualified`), the `_save_discord_guard` fallback omits TTL pruning, `log_candidates` has no FileLock, and the SGP `try/except ImportError` would let runtime errors crash the engine after the card has already posted.

## Findings

### MEDIUM

- **[MEDIUM]** `run_picks.py:3975` — **WHAT**: `log_candidates()` uses `datetime.now()` (no timezone) for `run_time`. **WHY WRONG**: Violates the project convention that every timestamp uses `ZoneInfo("America/New_York")`. On a machine where local TZ ≠ ET (e.g., UTC server, DST boundary), `run_time` in `pick_log_candidates.csv` is offset from ET pick_log dates, corrupting cross-file time comparisons. **FIX**: Replace with `datetime.now(ZoneInfo("America/New_York")).strftime("%H:%M")`.

- **[MEDIUM]** `run_picks.py:1028–1029, 2457` — **WHAT**: Two additional `datetime.now()` (no timezone) inside `check_gates()` (WNBA opening-gate) and `evaluate_props()` (WNBA early-season dampener). **WHY WRONG**: Same ET convention violation; on DST boundary nights the gate fires one game early/late. **FIX**: Replace both with `datetime.now(ZoneInfo("America/New_York")).date()`.

- **[MEDIUM]** `run_picks.py:5744–5745` — **WHAT**: Sanity-check line `All sizes ≤ 1.25u` (`all(p.get("size",0) <= 1.25 for p in all_qualified)`) always fails when a KILLSHOT is present. **WHY WRONG**: `select_killshots()` mutates `qualified` in-place (lines 5415–5416: `p["tier"] = "KILLSHOT"`, `p["size"] = _killshot_size(p)` which is 3–4u). `format_output` receives `qualified` (which still contains the mutated KILLSHOTs) as `all_qualified`. The ✗ fires on every run with a KILLSHOT, creating alert fatigue. **FIX**: Exclude KILLSHOT-tier picks from this check: `all(p.get("size",0) <= 1.25 for p in all_qualified if p.get("tier") != "KILLSHOT")`.

- **[MEDIUM]** `run_picks.py:6285–6288` — **WHAT**: H1 daily-cap enforcement (`_premium_u + _ks_total + _units_today > 12.0`) omits the current session's daily_lay and longshot unit sizes when checking whether KILLSHOT fits. **WHY WRONG**: `alt_spread_parlay` and `safest6_parlay` are built at lines 6353–6357, after H1 enforcement. A session with 6u premium + 2u KILLSHOT + 0.5u daily_lay + 0.25u longshot = 8.75u total — fits under 12u — but if premium is 8u + 3u KILLSHOT + 0.75u lay = 11.75u (under cap), it should be flagged. More concretely: the `format_output` checker at line 5746 DOES include `_lay_u + _longshot_u` in the display total, but the enforcement loop at 6285 does not. **FIX**: Build `alt_spread_parlay` and `safest6_parlay` before H1 check, or estimate parlay sizes when checking KILLSHOT fit.

- **[MEDIUM]** `run_picks.py:6467` — **WHAT**: Manual game-line picks are logged with `run_type = "gameline"` (not a valid schema run_type). **WHY WRONG**: The schema `run_type` enum is `primary | bonus | manual | daily_lay | sgp | longshot`. "gameline" is not in it. `analyze_picks.py` and `grade_picks.py` filtering by run_type will miss or misclassify these rows. Affects `pick_log_manual.csv` only, but the schema promise is broken. **FIX**: Change to `"manual"` for all manual picks regardless of stat type (the `stat` column already identifies game-line stats; the pick_type distinction is redundant in run_type).

- **[MEDIUM]** `run_picks.py:6629–6646` — **WHAT**: The SGP `try/except` block only catches `ImportError`. If `run_sgp_builder()` raises any other exception (network timeout, ValueError, KeyError), the entire `main()` crashes after the premium card has already posted and picks have been logged. **WHY WRONG**: SGP is a best-effort "fun bet" feature; a crash here is high impact on an already-completed run. The print("Done. Let's eat.") and `_run_lock` release never execute, leaving the run-lock held until OS reaps it. **FIX**: Change to `except Exception as e: print(f"  [SGP] Error: {e} — skipping.")` or add a broad except inside the existing try block around the `run_sgp_builder()` call specifically.

- **[MEDIUM]** `run_picks.py:5148–5153` — **WHAT**: Bonus 12u cap check at line 5150 uses `best.get("size", 1.25)` (base sizing from `size_picks_base`) but the actual posted/logged size is the VAKE-resized value from `size_bonus_pick()` computed at line 5161 (after the check). **WHY WRONG**: If `size_bonus_pick()` returns a larger value than base sizing (e.g., T2 pick: base=0.75u, VAKE=1.00u), the cap check passes at the lower estimate but the actual bet is larger. In edge cases near the 12u ceiling this could push total units over cap. **FIX**: Move the size check to after `size_bonus_pick()` has run (i.e., move lines 5149–5153 to after line 5172), using the resized value.

### LOW

- **[LOW]** `run_picks.py:251–254` — **WHAT**: `SHADOW_LOG_PATHS` has a `"MLB"` entry pointing to `pick_log_mlb.csv`, but `SHADOW_SPORTS = {"WNBA"}`. The MLB log path is dead code. **WHY WRONG**: MLB went live on 2026-05-20 and is no longer a shadow sport. The MLB entry in `SHADOW_LOG_PATHS` iterates at line 6206 but produces an empty list every time. Confusing to auditors. **FIX**: Remove the `"MLB"` key from `SHADOW_LOG_PATHS`.

- **[LOW]** `run_picks.py:4424, 5503–5504, 5596` — **WHAT**: `build_premium_embed()` uses `premium[:5]` and the output formatter iterates `premium[:5]` and states "Max 5 Positions", but `MAX_PREMIUM_PICKS = 3` (per-sport cap). The verification checklist at line 5731 checks `n_prem == MAX_PREMIUM_PICKS` (3). **WHY WRONG**: The `[:5]` slices are harmless (the list will have at most 3 items), but the "Max 5 Positions" hardcoded text in the Discord copy/paste block (line 5596) is factually wrong and will be pasted into the server. **FIX**: Change the hardcoded string to "Max 3 Positions (per sport)" or use `MAX_PREMIUM_PICKS`.

- **[LOW]** `run_picks.py:4304–4310` — **WHAT**: The `_save_discord_guard` fallback path (reached when `atomic_write_json` fails) writes the `guard` dict without calling `_prune_discord_guard(guard)`. **WHY WRONG**: The main path prunes entries older than 90 days; the fallback does not. On repeated fallback invocations the guard file grows indefinitely. **FIX**: Change line 4306 to `json.dump(_prune_discord_guard(guard), f, indent=2)`.

- **[LOW]** `run_picks.py:3992` — **WHAT**: `log_candidates()` opens `pick_log_candidates.csv` without a `FileLock`. **WHY WRONG**: Inconsistent with every other pick log write in the codebase. If two runs execute concurrently (unlikely but possible with `--no-sgp` + research mode), interleaved writes could corrupt the CSV. The process-level `run_picks.lock` at line 5864–5868 should prevent concurrent runs from the same process, but an external script that calls `log_candidates` directly would not be protected. **FIX**: Wrap the `open()` call at line 3992 in `with _pick_log_lock(path):`.

- **[LOW]** `run_picks.py:6171, 6433` — **WHAT**: `today_str` is assigned twice in `main()` — line 6171 and line 6433 — both as `datetime.now(ZoneInfo("America/New_York")).strftime("%Y-%m-%d")`. **WHY WRONG**: Redundant. The second assignment is after the `format_output` call and before the Discord posting section. Since both use ET with ZoneInfo, they will always agree during normal operation. However, if a run spanning midnight ET (pathological case) executes between the two assignments, `today_str` for Discord post keys would disagree with the already-logged pick dates from line 6171. **FIX**: Remove the re-assignment at line 6433; use the single `today_str` from line 6171 throughout.

- **[LOW]** `run_picks.py:3279–3283` — **WHAT**: `evaluate_nrfi()` builds the `matchup_abbrev` display string using a raw substring loop over `TEAM_ABBREV` (`if full_name in game.lower()`) rather than `resolve_team_abbrev()`. **WHY WRONG**: Inconsistent with the explicit fix applied to pitcher matching (lines 3254–3257 use `resolve_team_abbrev()`). This cosmetic field appears in the Discord embed for NRFI/YRFI picks. If a team name substring matches multiple entries in TEAM_ABBREV, `matchup_parts` could have more than 2 entries, and `[:2]` would silently truncate. **FIX**: Use `resolve_team_abbrev(home)` and `resolve_team_abbrev(away)` directly since both are in scope.

- **[LOW]** `run_picks.py:4151` — **WHAT**: `log_picks()` always hardcodes `run_type = "primary"` regardless of what is being logged. This affects WNBA shadow picks (logged to `pick_log_wnba.csv` via `log_path_override`) and shadow_stats picks (logged to `pick_log_shadow_stats.csv`). **WHY WRONG**: Shadow logs have `run_type="primary"` for all rows, which is misleading for auditing/analysis. `analyze_picks.py --shadow` would show all picks as run_type=primary, making it impossible to distinguish premium card picks from shadow stats re-enabled picks. **FIX**: Add a `run_type` parameter to `log_picks()` defaulting to `"primary"`, and pass `"shadow"` (or similar) when called for shadow logs.

- **[LOW]** `run_picks.py:4714–4716` — **WHAT**: `_log_daily_lay()` returns silently (no log entry) if `pick_log.csv` does not exist (`if not log_path.exists(): return`). **WHY WRONG**: If this is the very first run of the day and the main `log_picks()` write hasn't happened yet (e.g., a `--no-save` run that manually calls `_log_daily_lay`), or the file was accidentally deleted, the daily lay disappears from the ledger without any warning. **FIX**: Log a `logger.warning(...)` before returning, matching the pattern used elsewhere.

### OPEN_QUESTION

- **[OPEN_QUESTION]** `run_picks.py:6309–6347` — **WHAT**: The `log_picks()` call at line 6342 (`log_picks(premium + killshots, ...)`) logs KILLSHOT picks with `run_type="primary"`. The schema comment in CLAUDE.md says run_type is `primary | bonus | manual | daily_lay | sgp | longshot`. Is `run_type="primary"` the intended canonical value for KILLSHOT ledger rows, or should KILLSHOT rows have `run_type="killshot"`? `_killshots_this_week()` identifies them via `tier == "KILLSHOT"`, not run_type, so the cap works correctly. But `analyze_picks.py` filtering by run_type on KILLSHOT rows would need to look for "primary" tier="KILLSHOT", which is non-obvious. **WHY**: Confirm with Jono whether KILLSHOT run_type is intentionally "primary" or should be a distinct value.

- **[OPEN_QUESTION]** `run_picks.py:4026–4195` — **WHAT**: `log_picks()` docstring says "Columns: date, run_time, sport, player, team, stat, line, direction, proj, win_prob, edge, odds, book, tier, pick_score, size, game, mode" (18 columns from an old docstring) but actually writes 29 columns. **WHY**: The docstring hasn't been updated since the schema expanded to v4. Not a runtime bug, but confusing to future developers. **FIX**: Update docstring to match actual column list or reference `CANONICAL_HEADER`.
